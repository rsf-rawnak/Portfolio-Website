Teaching a Machine to Hear Tool Wear

~7 min read LOF · OC-SVM · FFT KIT Karlsruhe Dataset

A CNC milling machine doesn't announce when its cutting tool is going bad. It keeps running, keeps cutting, keeps producing parts — right up until the tool fails and takes a workpiece, a tolerance, or a production run with it. In most factories, tools get replaced on a fixed schedule instead, whether they need it or not. That's the problem my thesis sits inside: can a machine learning model tell you a tool is degrading before a human would notice, without ever being shown a single labeled example of "this is a worn tool"?

That "without labels" part is the whole challenge. In a research lab you can label everything — this cut was good, this cut was bad. On a real factory floor, nobody has time to hand-label thousands of milling passes. So the model has to learn what normal sounds and looks like from vibration and sensor data, and flag anything that drifts too far from it. That's unsupervised anomaly detection, and it's a much harder problem than standard classification.

Where the signal actually lives

Raw sensor data — vibration, acoustic emission, spindle current — is mostly noise if you look at it in the time domain. The useful information about tool wear lives in the frequency domain: how the vibration's frequency content shifts as a cutting edge dulls. So the pipeline starts with FFT-based feature extraction, converting raw time-series signal into spectral features that actually carry a wear signature. We ran this against the KIT Karlsruhe milling dataset, working across multiple tools on the same machine to see whether a model trained on one tool's behavior could generalize to another.

Two ways to define "abnormal"

We used two anomaly detection approaches side by side rather than betting on one. Local Outlier Factor (LOF) flags a point as anomalous based on how isolated it is relative to its local neighborhood in feature space — good at catching wear patterns that don't fit a single global shape. One-Class SVM instead learns a boundary around what "normal" looks like and flags anything that falls outside it. Neither is strictly better; they fail in different ways, which is exactly why running both matters when there's no ground truth to check against.

The part that actually matters for deployment

A model that only works on the exact tool it was trained on is a lab result, not a solution. Real factories swap tools constantly. So a chunk of the work went into cross-tool transferability — testing whether thresholds and detectors calibrated on one tool still hold up on a different one, and using domain adaptation techniques to close that gap when they didn't. That's the difference between a thesis chapter and something a plant engineer could actually trust.

What I took from it

The honest version: anomaly detection without labels forces you to be rigorous about how you evaluate yourself, because there's no easy accuracy number to lean on. You have to build confidence through multiple detectors agreeing, through domain knowledge about what a worn tool physically does to a signal, and through testing generalization instead of just fitting one dataset well. That mindset — don't trust a single clean metric, stress-test for the case where your assumptions break — is the same one I've carried into every project since.
